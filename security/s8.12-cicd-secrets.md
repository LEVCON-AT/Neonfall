## 1. Quality Gates in GitHub Actions

### Workflow-Struktur (deploy.yml)

```
Push auf main →
  ├── quality (Lint + Build + Audit + Secrets Scan)
  │   ✅ alle grün →
  └── deploy (SSH → VPS → vps-update.sh)
```

### Quality Gate Steps

| Step | Was | Blockiert Deploy? | Status |
|------|-----|-------------------|--------|
| Lint | `bun run lint` (ESLint) | ✅ Ja | ✅ |
| Build | `bun run build` (Next.js standalone) | ✅ Ja | ✅ |
| Dependency Audit | `bun audit --prod` (critical only) | ✅ Ja | ✅ |
| Secrets Scan | grep für ghp_/sk-/AKIA Patterns | ✅ Ja | ✅ |
| TypeScript Check | `npx tsc --noEmit` | ❌ Info only | ✅ |

### Deploy Step (nach Quality Gates)
- `needs: quality` — Deploy läuft nur wenn Quality grün ist
- `if: github.ref == 'refs/heads/main'` — nur auf main branch

## 3. Release-Gate Prozess

```
1. Code-Änderung → Commit → Push auf main
2. Quality Gates laufen:
   ├── Lint (ESLint) — 0 errors
   ├── Build (Next.js) — success
   ├── Audit (bun audit --prod) — 0 critical
   └── Secrets Scan — clean
3. Wenn alle grün → Deploy läuft
4. Deploy: SSH → VPS → vps-update.sh
5. Health Check: HTTP 200 auf neonfall.levcon.ai
6. Wenn Deploy fehlschlägt → Rollback (Backup wird in vps-update.sh erstellt)
```
