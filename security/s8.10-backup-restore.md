## 1. Backup

### Was wird gesichert?

| Komponente | Pfad |频率 | Methode |
|-----------|------|---------|---------|
| SQLite DB | /var/www/neonfall/db/neonfall.db | Täglich 03:00 | sqlite3 dump → gzip |
| .env (Secrets) | /var/www/neonfall/.env | Täglich 03:00 | Datei-Kopie |
| nginx config | /etc/nginx/sites-available/neonfall.levcon.ai | Täglich 03:00 | Datei-Kopie |
| systemd units | /etc/systemd/system/neonfall*.service | Täglich 03:00 | Datei-Kopie |
| Prisma schema | /var/www/neonfall/prisma/schema.prisma | Täglich 03:00 | Datei-Kopie |

### Backup-Script: `deploy/scripts/backup.sh`

Erstellt einen Tarball mit allen Komponenten:
```
/var/backups/neonfall/neonfall-20260724_030000.tar.gz
  ├── neonfall-20260724_030000-db.sql.gz    (SQLite dump)
  ├── neonfall-20260724_030000-env          (.env)
  ├── neonfall-20260724_030000-nginx.conf   (nginx config)
  ├── neonfall-20260724_030000-neonfall.service
  ├── neonfall-20260724_030000-neonfall-mp.service
  └── neonfall-20260724_030000-schema.prisma
```

### Retention
- **30 Tage** — Backups älter als 30 Tage werden automatisch gelöscht
- **Storage:** `/var/backups/neonfall/` (lokal auf VPS)

### Cron (bereits in deploy.sh eingerichtet)
```cron
# /etc/cron.d/neonfall-backup
0 3 * * * root bash /var/www/neonfall/deploy/scripts/backup.sh
```

## 2. Restore

### Restore-Script: `deploy/scripts/restore.sh`

**Aufruf:**
```bash
sudo bash /var/www/neonfall/deploy/scripts/restore.sh /var/backups/neonfall/neonfall-20260724_030000.tar.gz
```

**Schritte:**
1. Tarball extrahieren
2. Services stoppen (neonfall + neonfall-multiplayer)
3. DB wiederherstellen (gunzip → sqlite3 import)
4. .env wiederherstellen
5. nginx config wiederherstellen + reload
6. systemd units wiederherstellen + daemon-reload
7. Services starten
8. Verifikation (service active + HTTP 200)

## 3. Disaster Recovery

### RTO (Recovery Time Objective)

| Szenario | RTO | Methode |
|----------|-----|---------|
| DB Corruption | ~5 min | restore.sh |
| .env verloren | ~2 min | restore.sh oder manuell |
| nginx config kaputt | ~2 min | restore.sh oder git pull |
| VPS komplettausfall | ~30 min | Neu-Deployment via deploy.sh + restore.sh |

### RPO (Recovery Point Objective)

| Komponente | RPO | Begründung |
|-----------|-----|------------|
| Scores | ≤24h | Tägliche Backups um 03:00 |
| Player-Daten | ≤24h | Tägliche Backups um 03:00 |
| Config | ≤24h | Tägliche Backups um 03:00 |

**RPO = 24 Stunden** (maximal 1 Tag Datenverlust bei komplettem Ausfall)

### Recovery-Prozedur (Complete VPS Loss)

```bash
# 1. Neuen VPS aufsetzen (Ubuntu 22.04+)
# 2. DNS auf neue IP umleiten
# 3. Initial Deployment
cd /tmp
git clone git@github.com:LEVCON-AT/Neonfall.git neonfall-deploy
cd neonfall-deploy
sudo bash deploy/scripts/deploy.sh

# 4. Neuestes Backup auf neuen VPS kopieren
scp /path/to/neonfall-backup.tar.gz root@<new-ip>:/var/backups/neonfall/

# 5. Restore
sudo bash /var/www/neonfall/deploy/scripts/restore.sh /var/backups/neonfall/neonfall-backup.tar.gz

# 6. Verifikation
curl -sI https://neonfall.levcon.ai/ | head -3
systemctl status neonfall
```

## 4. Offsite-Backup (Empfehlung)

Aktuell sind Backups **lokal auf dem VPS**. Bei komplettem VPS-Verlust sind auch die Backups weg.

**Empfehlung:** Offsite-Backup via rsync oder S3:
```bash
# Täglicher rsync zu Backup-Server (z.B.另一VPS)
rsync -avz /var/backups/neonfall/ backup@<backup-server>:/backups/neonfall/

# Oder: S3 Upload
aws s3 sync /var/backups/neonfall/ s3://neonfall-backups/
```

**Priorität:** Mittel (für S8.14 Staging)
